Topic 01 | Foundations: Requirements & System Overview
System Architecture & Core Project Objectives
Review 1 & 2 Context
Problem Statement & Educational Motivation
  • Physical Register Bottlenecks: Paper registers suffer from physical tear, illegible handwriting, human tally errors, and vulnerability to proxy sign-ins.
  • Administrative Collation Bottleneck: Faculty spend hours collating daily sheets to compute aggregate percentages across 60+ students per batch.
  • Delayed Debarment Warnings: Students falling below the mandatory 75% attendance threshold are identified at semester end, preventing timely remedial intervention.
  • The Digital Solution: An atomic web roll-call engine with real-time aggregation recalculation, dynamic threshold alerts, and instant CSV audit exports.

    • React 19 Single Page Application built with Vite.
    • Tailwind CSS responsive design + Lucide icons.

  • Application Layer (Backend):
    • Node.js & Express.js REST API service.
    • Mongoose ODM schema validation and type modeling.
    • Bcrypt salted password hashing + JWT authentication.
  • Database Layer (MongoDB Engine):
    • 6 collections with 2,640+ seeded documents.
    • B-Tree compound indexing & multi-stage pipeline engine.

Topic 02 | Foundations: Schema Modeling & Justification
Database Selection (Why MongoDB?) & 6 Collections Schema
Review 1 & 2 Context
Why MongoDB? (Architectural Justification)
  • Flexible BSON Document Model: JSON objects naturally match JavaScript/React client models without complex SQL migrations.
  • Referencing vs. Embedding Decision:
    • Why NOT embed in Students? 50+ records per student causes document bloat toward the 16MB BSON limit and slows queries.
    • Normalized Referencing Solution: Attendance logs reference Student, Subject, and Class via ObjectIds, enabling fast queries and date-based indexing.
  • Native Aggregation Engine: Grouping, date bucketing, and percentages calculated directly on the database engine.
  • High-Throughput Bulk Operations: bulkWrite() handles hundreds of daily attendance records in a single network round-trip.
6 Master Collections Schema Design
1. Users

_id, name, email (unique), password (bcrypt), role ('admin'|'faculty'|'student')

2. Students

_id, regNo (unique index), name, email, department, year, semester, section ('D1'|'D2')

3. Faculty

_id, facultyId (unique), name, email, department

4. Subjects

_id, subjectCode (unique), subjectName, facultyId -> Faculty, credits

5. Classes

_id, subjectId -> Subject, facultyId -> Faculty, date, room, startTime, endTime

6. Attendance

_id, classId, studentId, subjectId, date, status ('Present'|'Absent'), markedBy

    User submits credentials $\rightarrow$ bcrypt validates salted hash $\rightarrow$ signed JWT token returned and stored in localStorage.

The Problem: Naive Iterative Saves Anti-Pattern
  • Sequential Insertion: for (let r of records) { await Attendance.create(r); }
  • 60 Sequential Round-Trips: Takes 1,500ms+ per roll-call session.
  • Partial Failure Risk: If record #30 drops due to network glitch, database is left in a corrupted state.
The Solution: Atomic bulkWrite() Upsert Engine
Naive Loop: 60 Network Round-Trips ~1,500 ms
Atomic bulkWrite() Upsert Engine < 12 ms (>99% faster!) 
Attendance.bulkWrite(records.map(r => ({
  updateOne: { filter: { studentId: r.studentId, subjectId: r.subjectId, date: r.date },
               update: { $set: { status: r.status, markedBy: req.user.id } }, upsert: true }
})));

Topic 05 | Review 3 Criterion 2: Advanced Queries & Analytics
Advanced Aggregation Framework: 7 Multi-Stage Pipelines
Criterion 2: 2 Marks
1. Student & Subject Analytics
  • Pipeline 1: Student Attendance %
    • $group by studentId: tally total & present.
    • $project: percentage = (present / total) * 100.
    • $lookup student info & $sort descending.
    • Output: Full student league rankings.
  • Pipeline 2: Subject-wise Turnout
    • $group by subjectId.
    • $project subject attendance rate.
    • $lookup subject details & $sort.
    • Powers Dashboard Subject Bar Chart.
2. Trends & Defaulter Tracker
  • Pipeline 3: Daily Attendance Trends
    • $group by $dateToString('%Y-%m-%d').
    • Accumulate totalPresent & totalAbsent.
    • $sort date ascending (+1).
    • Powers Daily Trend Line Chart.
  • Pipeline 4: Defaulters (<75% Threshold)
    • $group: aggregate per student.
    • $project: calculate exact percentage.
    • $match: filter percentage < threshold.
    • $lookup student details & $sort ascending.
3. Cohort & Institutional Stats
  • Pipeline 5: Monthly Report
    • Uses date operators: $year and $month.
    • Groups 2,640+ logs into monthly turnout buckets.
    • Powers Dean's monthly reviews.
  • Pipeline 6: Section Comparison
    • $lookup students & $group on section.
    • Compares Section D1 (86.5%) vs Section D2 (73.0%).
  • Pipeline 7: Overall Summary
    • $group with _id: null for system-wide stats in 1 scan.

Topic 07 | Review 3 Criterion 3 (Contd.): Security & Performance
Security Architecture, B-Tree Indexing & Query Tuning
Criterion 3: 1.5 Marks
B-Tree Indexing & Performance Tuning (<1.2ms)
  • Unique Single-Field Indexes: students.regNo, users.email, subjects.subjectCode, faculty.facultyId.
  • Compound Unique Index on Attendance:
    AttendanceSchema.index({ studentId: 1, subjectId: 1, date: 1 }, { unique: true });
    Prevents duplicate roll-call entries and powers atomic bulkWrite upserts.
  • Time-Series & Filter Indexes:
    attendance: { date: 1 }, { subjectId: 1, date: 1 }, and students: { department: 1, section: 1 }.
  • Execution Benchmark (COLLSCAN vs IXSCAN):
    • COLLSCAN: docsExamined = 2,640, executionTime = ~28.4ms.
    • IXSCAN: docsExamined = 1, executionTime = <1.2ms (Over 23x speedup!). 
db.attendances.find({ studentId: ..., date: ... }).explain('executionStats')
-> stage: 'IXSCAN', indexName: 'studentId_1_subjectId_1_date_1'
Security Architecture & Document Validation
  • Bcrypt Password Hashing: Passwords encrypted with 10 salt rounds prior to storage. Plaintext passwords never touch database or logs.
  • Stateless JWT Authentication: Signed tokens with user claims (id, role, expiry) returned on login and passed via x-auth-token header.
  • Role-Based Access Control (RBAC): Admin (full CRUD), Faculty (roll-call and subject reports), Student (personal attendance).
  • Injection Prevention & Input Validation: Strict Mongoose schema typing automatically sanitizes query selectors; CORS configured to prevent CSRF.
  • Schema Constraints: Required field constraints, enum validations, and referential integrity.

Technical Viva Voce Defense & Conclusion

Q1: Why choose MongoDB over MySQL?
Ans: Scalability to millions of records, native multi-stage aggregations without expensive JOINs, and high-throughput atomic bulk writes.

Q2: Why reference instead of embed attendance in Students?
Ans: Avoids the 16MB BSON limit, eliminates huge document bloat, and allows independent indexing on dates and subjects.

Q3: What makes bulkWrite idempotent?
Ans: Unique compound index { studentId, subjectId, date } ensures upsert updates existing records instead of generating duplicates.
